# Бодрый Боцман — внутренняя система управления

Веб-приложение для управления морскими прогулками, флотом и тюнинг-центром
компании «Бодрый Боцман». Система объединяет рейсы, расчёты с инвесторами,
зарплаты, заказы, задачи команды, складской учёт и финансовую аналитику.

Приложение написано на Flask, использует SQLite и серверные Jinja-шаблоны.
Интерфейс адаптирован для мобильных устройств и может устанавливаться как PWA.

## Возможности

### Зарплаты

- учёт выполненных работ, часов, ставок и начислений;
- недельные периоды и фильтр по сотруднику;
- отметка выплаты зарплаты;
- автоматическое создание начислений из рейсов и выполненных задач;
- гарантированный минимум за смену;
- расчёт гонорара менеджера по продажам;
- отправка выплат самозанятым через Т-Банк.

### Рейсы и инвесторы

- учёт катера, времени, вида рейса, канала продажи и выручки;
- несколько сотрудников в одном рейсе;
- учёт топлива, стоянки и дополнительных расходов;
- автоматический расчёт комиссии, остатка и выплаты инвестору;
- формирование договоров в DOCX;
- отдельный кабинет инвестора с данными только по его катерам.

Расчёт рейса:

```text
Комиссия       = Выручка × Процент комиссии
Прямые расходы = Оплата команды + Топливо + Стоянка + Прочие расходы
Остаток        = Выручка − Комиссия − Прямые расходы
Инвестору      = Остаток / 2
Компании       = Комиссия + Остаток / 2
```

### Импорт из Yclients

- загрузка записей и групповых событий за выбранный период;
- определение катера по цвету записи;
- сопоставление услуг с видами рейсов;
- распознавание прямых продаж и агрегаторов;
- объединение записей одного рейса с несколькими сотрудниками;
- защита от повторного импорта;
- очередь проверки перед созданием рейса;
- автоматическая проверка смен и доплат до минимальной ставки.

Импорт не создаёт обычный рейс без проверки: кандидат сначала попадает в
очередь, где администратор может исправить данные, подтвердить или пропустить
его.

### Флот

- карточка каждого катера;
- расчётный остаток топлива и журнал заправок;
- автоматическое списание топлива по завершённым групповым рейсам YCLIENTS;
- очередь индивидуальных рейсов для ручного указания расхода;
- хранение судовых документов;
- предрейсовые и послерейсовые чек-листы;
- фотографии обнаруженных проблем;
- реестр дефектов и их статусы;
- назначение устранения дефекта сотруднику;
- преобразование выполненной задачи в начисление зарплаты.

### Тюнинг-центр

- клиентская база и заказы на обслуживание лодок;
- состав заказа: работы, товары, себестоимость, наценка и скидка;
- статусы заказа и отдельных работ;
- назначение работ сотрудникам;
- фотографии выполнения и внутренние заметки;
- напоминания по заметкам;
- интерактивные листы диагностики корпуса;
- автоматическое создание финансового проекта для каждого заказа;
- публичный кабинет клиента по уникальной ссылке;
- согласование клиентом отдельных работ;
- формирование актов в PDF и документов передачи.

Заявки с сайта на Tilda могут автоматически создавать новые заказы со
статусом «Новая заявка».

### Оплаты и чеки

- ручная регистрация платежей по заказу;
- онлайн-оплата через ЮKassa;
- обработка webhook ЮKassa;
- фискализация ручных платежей через МодульКассу;
- повторная отправка и проверка статуса чека;
- учёт оплаченной суммы и остатка по заказу.

### Аналитика

- импорт банковских операций из Т-Банка;
- ручное добавление операций, отсутствующих в выписке;
- назначение операции на проект или отдельную работу;
- распределение одной операции между несколькими проектами;
- расчёт доходов, расходов и прибыли проекта;
- включение в себестоимость зарплаты и списанных материалов;
- детализация рентабельности отдельных работ заказа.

### Склад и снабжение

- несколько складов;
- каталог материалов и товаров;
- приход, остатки и списания;
- единицы учёта: штуки, квадратные и погонные метры;
- фотографии товаров;
- минимальный остаток и автоматические заявки;
- заявки сотрудников на снабжение;
- списание материалов непосредственно из назначенной задачи;
- автоматическое списание товара, добавленного в заказ тюнинг-центра.

### Уведомления и автоматизация

- уведомления администратора и сотрудников через Telegram;
- браузерные push-уведомления через Web Push/VAPID;
- напоминания по заказам;
- cron-проверка смен капитанов;
- cron-проверка статусов чеков и отправка напоминаний.

### Сотрудники

- единый список сотрудников в административном интерфейсе;
- назначение и удаление должностей без редактирования исходного кода;
- получение личных Telegram-аккаунтов из сообщений боту;
- привязка, проверка и удаление персонального канала уведомлений;
- автоматический перенос ранее настроенных Telegram Chat ID.

## Роли и доступ

В приложении три защищённых кабинета и один клиентский интерфейс:

| Роль | Адрес | Доступ |
| --- | --- | --- |
| Администратор | `/admin/login` | Все операционные и финансовые разделы |
| Сотрудник | `/team/login` | Собственная зарплата, задачи, документы, чек-листы и заявки |
| Инвестор | `/investor/login` | Рейсы и выплаты только по связанным катерам |
| Клиент | `/client/<token>` | Свой заказ, согласование работ и диагностика |

Сессии подписываются ключом `SECRET_KEY`. Пароли хранятся в базе в виде
хешей Werkzeug. Начальные аккаунты задаются в `app.py`, а справочники флота —
в `modules/fleet/constants.py`; данные синхронизируются с базой при запуске.

## Как связаны основные данные

```text
Yclients → кандидат импорта → рейс → работа команды → зарплата
                              └────→ расчёт выплаты инвестору

Tilda/администратор → заказ тюнинг-центра → финансовый проект
                           ├→ работы → задачи сотрудников → зарплата
                           ├→ материалы/товары → складские списания
                           ├→ платежи → ЮKassa/МодульКасса
                           └→ банковские операции → прибыль проекта
```

Приложение постепенно переводится на модульную архитектуру. Флот и сотрудники
уже оформлены как Flask Blueprints с отдельными HTTP-, сервисными и SQL-слоями;
остальные разделы пока остаются в `app.py`. При импорте приложения вызывается
`init_db()`: функция создаёт отсутствующие таблицы, добавляет новые поля и
выполняет необходимые обратные заполнения данных.

## Локальный запуск

Требуется Python 3.11.

```bash
git clone https://github.com/bodrbo/-.git bodrbo-app
cd bodrbo-app
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python app.py
```

Приложение будет доступно по адресу <http://127.0.0.1:5000>.

При первом запуске рядом с `app.py` создастся `workhours.db`. Существующая
база будет автоматически обновлена встроенными миграциями.

## Переменные окружения

Для локальной разработки можно экспортировать переменные в shell. На Beget
они загружаются из файла `.env` рядом с `passenger_wsgi.py`.

### Основные

| Переменная | Назначение |
| --- | --- |
| `SECRET_KEY` | Подпись пользовательских сессий |
| `WORKHOURS_DB_PATH` | Необязательный путь к SQLite-файлу; используется для изоляции тестов |
| `YCLIENTS_PARTNER_TOKEN` | Партнёрский токен Yclients |
| `YCLIENTS_USER_TOKEN` | Пользовательский токен Yclients |
| `YCLIENTS_COMPANY_ID` | ID филиала Yclients |
| `CRON_SECRET` | Защита внутренних cron-эндпоинтов |

### Платежи и банк

| Переменная | Назначение |
| --- | --- |
| `YOOKASSA_SHOP_ID` | ID магазина ЮKassa |
| `YOOKASSA_SECRET_KEY` | Секретный ключ ЮKassa |
| `TBANK_API_TOKEN` | Доступ к выписке Т-Банка |
| `TBANK_API_TOKEN_PAYMENT` | Создание выплат самозанятым |
| `TBANK_ACCOUNT_NUMBER` | Номер расчётного счёта |
| `MODULKASSA_USERNAME` | API-логин МодульКассы |
| `MODULKASSA_PASSWORD` | API-пароль МодульКассы |
| `MODULKASSA_ENV` | `production` для боевого контура |

### Интеграции и уведомления

| Переменная | Назначение |
| --- | --- |
| `TILDA_WEBHOOK_SECRET` | Проверка webhook от Tilda |
| `TELEGRAM_BOT_TOKEN` | Токен Telegram-бота |
| `TELEGRAM_BOT_USERNAME` | Необязательное имя бота без `@` для ссылки из раздела сотрудников |
| `TELEGRAM_CHAT_ID` | Основной административный чат |

Пример `.env` без реальных секретов:

```dotenv
SECRET_KEY=replace-with-a-long-random-value

YCLIENTS_USER_TOKEN=...
YCLIENTS_COMPANY_ID=...
CRON_SECRET=...
```

Не добавляйте `.env`, токены, пароли, банковские реквизиты или рабочую базу
данных в Git.

## Production

Репозиторий содержит два варианта запуска:

```bash
gunicorn app:app
```

или через Phusion Passenger, который импортирует объект `application` из
`passenger_wsgi.py`.

На текущем Beget-хостинге фактический Passenger loader может находиться
уровнем выше каталога репозитория. При изменении логики загрузки `.env`
необходимо синхронно обновлять и серверный loader.

### Почасовая синхронизация топлива

На Beget необходимо раз в час вызывать защищённый маршрут:

```bash
curl -fsS "https://ВАШ-ДОМЕН/internal/cron/sync-fuel?token=ЗНАЧЕНИЕ_CRON_SECRET"
```

При временном сбое система на следующем успешном запуске повторно запрашивает
период от последней синхронизации; повторное списание исключено уникальными
идентификаторами событий YCLIENTS.

Синхронизация считает проведённым завершившийся рейс, если запись не удалена
и не имеет статуса «Не пришёл». Групповое событие списывается один раз вне
зависимости от количества клиентов и сотрудников внутри него. Обычная запись
попадает в очередь ручного расхода.

Учёт каждого катера начинается отдельно: первая заправка с отметкой «Бак
заправлен до полного» устанавливает остаток равным физической ёмкости. Рейсы,
начавшиеся раньше этого момента, в топливный журнал не попадают.

SQLite подходит для текущего небольшого внутреннего сервиса, но файл базы
должен находиться на постоянном диске и регулярно копироваться. Запуск
нескольких одновременно пишущих экземпляров приложения без миграции на
серверную СУБД не рекомендуется.

## Резервное копирование

Критичные пользовательские данные находятся в `workhours.db`. Кроме базы,
необходимо сохранять загруженные документы и фотографии в каталогах внутри
`static/`.

Перед обновлением production рекомендуется сделать копии:

```text
workhours.db
static/boat_documents/
static/work_photos/
static/checklist_photos/
static/supply_photos/
static/diplomas/
```

## Безопасность

- все секреты должны поступать только из окружения или серверного `.env`;
- production обязательно должен иметь постоянный `SECRET_KEY`;
- внутренние диагностические и cron-маршруты должны быть закрыты
  `CRON_SECRET`;
- перед публикацией изменений проверяйте репозиторий на случайно добавленные
  токены и пользовательские данные;
- при компрометации секрета его нужно отозвать у провайдера, а не только
  удалить из истории Git.
